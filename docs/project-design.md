# t-cex-trade 项目背景与详细设计

## 1. 项目背景

### 1.1 背景说明

`t-cex-trade` 是一个简化版中心化交易所交易系统，面向 Java 后端工程师学习 CEX 核心链路与准备高级后端面试。

CEX 的核心交易链路本质上是中心化高并发金融系统，重点不在智能合约或链上协议，而在订单、撮合、资金、账务、消息、风控、对账与系统稳定性。对 Java 后端岗位来说，这类项目可以集中体现生产系统中最有价值的能力：正确性、一致性、性能、可恢复性和工程化。

本项目会从单交易对 `BTC/USDT` 入手，实现从模拟充值、下单冻结、撤单解冻、撮合成交、资金清算、事件通知到对账补偿的完整闭环。

### 1.2 项目目标

- 建立一套可讲清楚的 CEX 核心交易系统模型。
- 用项目串联 `Java`、`Spring Boot`、`MySQL`、`Redis`、`Kafka`、`JVM` 等核心后端技术。
- 重点训练资金正确性、消息最终一致性、订单状态机、异常补偿和系统设计表达。
- 为成都、远程、Web3/CEX Java 后端岗位准备一个可演示、可扩展、可写进简历的代表项目。

### 1.3 项目边界

第一阶段只做中心化交易系统内部链路：

- 用户资产
- 模拟充值
- 限价下单
- 撤单
- 内存撮合
- 成交记录
- 成交清算
- Kafka 事件
- 对账补偿

暂不做或后续再做：

- 真实链上充值提现
- 多链钱包
- 合约交易
- 杠杆、保证金、强平
- KYC/AML
- 完整撮合引擎高可用
- 真实低延迟网络协议

## 2. 业务总流程

### 2.1 核心链路

1. 用户模拟充值 `USDT` 或 `BTC`。
2. 用户提交限价买单或卖单。
3. 系统校验余额、交易对、价格、数量和风控规则。
4. 买单冻结计价资产，卖单冻结基础资产。
5. 订单进入订单簿。
6. 撮合引擎按价格优先、时间优先规则撮合。
7. 成交后生成成交记录。
8. 清算服务更新双方资产余额和资金流水。
9. 订单状态更新为部分成交、全部成交或撤单。
10. Kafka 发布订单、成交、资产变更事件。
11. 对账任务定期校验订单、成交、资产和流水是否一致。

### 2.2 示例

交易对：`BTC/USDT`

- 买单：用户 A 以 `30000 USDT` 买入 `0.1 BTC`，冻结 `3000 USDT`。
- 卖单：用户 B 以 `29900 USDT` 卖出 `0.1 BTC`，冻结 `0.1 BTC`。
- 撮合：买价大于等于卖价，按挂单价格成交。
- 清算：A 获得 `0.1 BTC`，B 获得成交金额，双方冻结资产扣减。

## 3. 功能模块设计

### 3.1 用户与账户模块

#### 模块职责

- 管理用户基础信息。
- 管理用户资产账户。
- 区分可用余额和冻结余额。
- 记录每一次资产变化流水。

#### 核心功能

- 创建用户。
- 查询用户资产。
- 模拟充值。
- 冻结资产。
- 解冻资产。
- 成交扣减冻结资产。
- 成交入账。
- 查询资金流水。

#### 关键规则

- 同一用户、同一币种只有一条资产余额记录。
- 余额变更必须产生资金流水。
- 可用余额不能为负。
- 冻结余额不能为负。
- 资金流水只追加，不修改，不删除。

#### 推荐表

- `user_account`
- `asset_balance`
- `asset_flow`

### 3.2 交易对模块

#### 模块职责

- 管理可交易的币对。
- 维护价格精度、数量精度和最小下单限制。

#### 核心功能

- 创建交易对。
- 启用或停用交易对。
- 查询交易对配置。

#### 示例配置

- 交易对：`BTC/USDT`
- 基础资产：`BTC`
- 计价资产：`USDT`
- 价格精度：2 位
- 数量精度：6 位
- 最小下单数量：`0.0001 BTC`

### 3.3 订单模块

#### 模块职责

- 接收用户下单请求。
- 校验订单参数和账户余额。
- 冻结下单资产。
- 创建订单记录。
- 管理订单状态流转。

#### 订单类型

第一阶段只支持：

- 限价买单
- 限价卖单

后续可扩展：

- 市价单
- IOC
- FOK
- Post Only

#### 订单状态

- `NEW`：已创建，未成交。
- `PARTIALLY_FILLED`：部分成交。
- `FILLED`：全部成交。
- `CANCELING`：撤单处理中。
- `CANCELED`：已撤单。
- `REJECTED`：已拒绝。

#### 状态流转

- `NEW -> PARTIALLY_FILLED`
- `NEW -> FILLED`
- `NEW -> CANCELING -> CANCELED`
- `PARTIALLY_FILLED -> FILLED`
- `PARTIALLY_FILLED -> CANCELING -> CANCELED`
- `NEW -> REJECTED`

#### 核心约束

- 已全部成交订单不能撤单。
- 已撤单订单不能再次成交。
- 订单成交数量不能超过委托数量。
- 订单剩余数量等于委托数量减去累计成交数量。
- 下单冻结和订单创建需要在同一事务内完成。

#### 推荐表

- `trade_order`
- `order_request`

### 3.4 撮合模块

#### 模块职责

- 维护交易对订单簿。
- 根据价格优先、时间优先规则撮合买卖订单。
- 生成成交记录。
- 推动订单状态变更和清算流程。

#### 第一版撮合规则

- 买单价格大于等于卖单价格时可以成交。
- 买盘价格高优先。
- 卖盘价格低优先。
- 同一价格下时间早优先。
- 支持部分成交。
- 成交价采用挂单价格。

#### 推荐内存结构

- 买盘：`TreeMap<BigDecimal, Queue<OrderBookItem>>`
- 卖盘：`TreeMap<BigDecimal, Queue<OrderBookItem>>`

买盘按价格倒序，卖盘按价格正序。

#### 核心输出

- 成交记录。
- 买方订单状态变更。
- 卖方订单状态变更。
- 清算事件。
- 行情事件。

#### 推荐表

- `trade_deal`
- `order_book_snapshot`

### 3.5 清算模块

#### 模块职责

- 根据成交结果更新买卖双方资产。
- 扣减冻结资产。
- 增加成交所得资产。
- 生成资金流水。

#### 买方清算

- 扣减冻结 `USDT`。
- 增加可用 `BTC`。
- 若成交价低于买单价格，释放多冻结的 `USDT`。

#### 卖方清算

- 扣减冻结 `BTC`。
- 增加可用 `USDT`。

#### 核心要求

- 清算必须幂等。
- 每笔成交只能清算一次。
- 资产变更和资金流水必须保持一致。
- 清算失败必须可重试。

#### 推荐表

- `settlement_record`
- `asset_flow`

### 3.6 Kafka 事件模块

#### 模块职责

- 解耦订单、撮合、清算、行情、通知、对账等模块。
- 承载核心业务事件。
- 支持失败重试、幂等消费和最终一致性。

#### 推荐事件

- `OrderCreatedEvent`
- `OrderCanceledEvent`
- `TradeMatchedEvent`
- `SettlementCompletedEvent`
- `AssetChangedEvent`
- `ReconcileFailedEvent`

#### Topic 设计

- `cex.order.event`
- `cex.match.event`
- `cex.settlement.event`
- `cex.asset.event`
- `cex.reconcile.event`
- `cex.dead-letter.event`

#### 幂等设计

- 每个事件携带全局唯一 `eventId`。
- 消费方写入 `event_consume_record`。
- 同一消费者组、同一 `eventId` 只能成功处理一次。
- 处理成功后记录消费状态。
- 处理失败进入重试或死信队列。

#### Outbox 设计

核心业务表和 `event_outbox` 在同一事务中写入，由后台任务或 CDC 机制发送 Kafka。

推荐表：

- `event_outbox`
- `event_consume_record`

### 3.7 Redis 模块

#### 模块职责

- 缓存交易对配置。
- 缓存盘口快照。
- 实现接口限流。
- 辅助热点数据读取。

#### 使用场景

- 交易对配置缓存。
- 用户短时间下单频控。
- 盘口快照缓存。
- 最新成交缓存。
- 分布式锁用于低频管理任务。

#### 注意事项

- 核心资金扣减不依赖 Redis 作为最终依据。
- Redis 可以用于加速读和限流，不能替代 MySQL 账务正确性。
- 缓存失效策略需要明确。
- 热点 key 需要监控。

### 3.8 对账与补偿模块

#### 模块职责

- 发现订单、成交、清算、资产、事件之间的不一致。
- 生成对账报告。
- 对可恢复异常执行补偿。

#### 对账项

- 订单累计成交数量是否等于成交记录汇总。
- 用户冻结余额是否等于未完成订单冻结金额汇总。
- 资产余额是否等于资金流水推导结果。
- 成交记录是否全部清算。
- outbox 事件是否全部发送。
- Kafka 事件是否全部消费成功。

#### 补偿策略

- 未发送事件重新发送。
- 未清算成交重新清算。
- 订单状态异常重新计算。
- 资金流水缺失进入人工审核。

#### 推荐表

- `reconcile_task`
- `reconcile_report`
- `compensation_task`

### 3.9 行情模块

#### 模块职责

- 根据成交记录生成简化行情。
- 提供最新成交和盘口查询。

#### 第一版功能

- 查询买卖盘口。
- 查询最近成交。
- 维护最新成交价。

#### 后续扩展

- K 线。
- 深度合并。
- WebSocket 推送。

### 3.10 风控模块

#### 模块职责

- 在下单前执行基础风控校验。
- 防止异常价格、异常频率和无效订单进入撮合。

#### 第一版规则

- 单用户每秒下单次数限制。
- 下单价格不能偏离最新价过大。
- 下单数量不能低于最小数量。
- 账户状态异常时拒绝下单。

#### 后续扩展

- 用户风险等级。
- 异常交易识别。
- 大额交易审核。
- AI 风险解释助手。

### 3.11 AI 辅助模块

#### 模块定位

AI 不进入撮合、清算、资金扣减等强确定性核心链路，只作为辅助能力接入。

#### 可选功能

- 交易异常解释助手。
- 风控规则问答助手。
- 运营数据分析助手。
- 日志故障归因助手。
- 内部知识库助手。

#### 技术方向

- `Spring AI` 或 `LangChain4j`
- RAG
- 向量数据库
- Tool Calling
- AI 调用限流
- 审计日志
- 成本统计

## 4. 技术选型

### 4.1 后端语言与框架

| 技术 | 选型 | 理由 |
| --- | --- | --- |
| JDK | `Java 21` | 当前主流 LTS，适合展示现代 Java 能力 |
| Web 框架 | `Spring Boot 3.x` | Java 后端岗位最通用，生态成熟 |
| 微服务扩展 | `Spring Cloud` | 后续可拆分订单、撮合、清算、资产服务 |
| ORM | `MyBatis` 或 `MyBatis Plus` | 国内 Java 岗位常见，SQL 可控 |
| 构建工具 | `Maven` | 简单稳定，面试项目足够 |

### 4.2 存储与中间件

| 技术 | 选型 | 理由 |
| --- | --- | --- |
| 关系数据库 | `MySQL 8` | 承载订单、资产、流水、清算等强一致数据 |
| 缓存 | `Redis` | 盘口、配置、限流、热点数据 |
| 消息队列 | `Kafka` | 交易事件流、异步解耦、最终一致性 |
| 搜索扩展 | `Elasticsearch` | 后续可用于订单和日志查询 |
| 内存数据结构 | Java 集合 | 第一版实现内存订单簿，便于理解撮合 |

### 4.3 可观测性与工程化

| 技术 | 选型 | 理由 |
| --- | --- | --- |
| 容器编排 | `Docker Compose` | 本地一键启动 MySQL、Redis、Kafka |
| 单元测试 | `JUnit 5` | 核心领域逻辑测试 |
| 压测 | `k6` 或 `JMeter` | 输出项目压测报告 |
| 指标监控 | `Prometheus` | 后续统计 QPS、延迟、错误率 |
| 可视化 | `Grafana` | 展示交易链路指标 |

### 4.4 AI 相关选型

| 技术 | 选型 | 理由 |

## 8. 非功能要求

### 8.1 正确性

- 资金变更必须可追溯。
- 订单和资产变更必须幂等。
- 清算失败必须可重试。
- 对账能发现关键不一致。

### 8.2 性能

- 下单接口需要支持并发请求。
- 盘口查询优先走缓存。
- 撮合模块避免频繁数据库交互。
- Kafka 消费端需要能处理积压。

### 8.3 可恢复性

- 服务重启后可以从数据库恢复订单簿。
- 未发送事件可以由 outbox 重发。
- 未清算成交可以由补偿任务重试。
- 异常资金流水需要进入人工审核队列。

### 8.4 可观测性

- 记录订单创建、撤单、成交、清算、补偿关键日志。
- 暴露接口耗时、撮合耗时、Kafka 积压、失败事件数量等指标。

## 10. 面试讲解重点

### 10.1 可以重点讲的问题

- 为什么资金流水必须不可变。
- 下单冻结和订单创建如何保证一致。
- Kafka 消息发出失败怎么办。
- 消费重复导致重复清算怎么办。
- 撤单和成交并发时如何处理。
- 服务重启后订单簿如何恢复。
- Redis 在交易系统里能做什么，不能做什么。
- AI 为什么不进入撮合和清算核心链路。

### 10.2 推荐简历亮点

- 设计资产账户模型，区分可用余额与冻结余额，通过不可变资金流水保证资产变更可追溯。
- 实现限价订单状态机，支持下单、撤单、部分成交、全部成交和异常状态保护。
- 基于内存订单簿实现价格优先、时间优先撮合，支持单交易对部分成交。
- 使用 Kafka 和 outbox 模式解耦订单、撮合、清算事件，保障消息最终一致性。
- 设计消费幂等、失败重试、死信队列和对账补偿机制，降低异常场景下的数据不一致风险。
- 引入 Redis 支撑盘口缓存、交易对配置缓存和下单限流，但不把 Redis 作为资金正确性的最终依据。
- 规划 AI 辅助模块，用于风控规则解释、日志归因和内部知识库，不影响核心交易链路确定性。
