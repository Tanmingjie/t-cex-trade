# t-cex-trade 功能学习地图

这份文档用于把项目功能点和需要补的知识模块一一对应起来。开发时不要先把所有理论学完，而是按功能推进：做到哪个功能，就补对应知识，写代码、做测试、整理面试表达。

## 1. 总体学习顺序

推荐顺序：

1. 应用脚手架与本地环境
2. 用户资产与资金流水
3. 交易对与风控校验
4. 订单生命周期
5. 内存订单簿与撮合
6. 成交清算
7. Kafka 事件与 outbox
8. Redis 缓存与限流
9. 对账与补偿
10. 行情查询
11. 可观测性与压测
12. AI 辅助模块

核心原则：

- 先保证资金正确，再追求性能。
- 先做同步闭环，再引入 Kafka 异步事件。
- 先单交易对、单节点撮合，再考虑扩展。
- AI 只做辅助解释，不进入撮合、清算和资金变更核心链路。

## 2. 应用脚手架与本地环境

### 功能点

- Spring Boot 应用启动。
- Maven 依赖管理。
- MySQL、Redis、Kafka 本地环境。
- Actuator health 健康检查。
- 模块包结构划分。

### 需要学习的知识模块

- `Maven`：生命周期、依赖管理、父 POM、scope、插件。
- `Spring Boot`：自动配置、starter、配置文件、profile、Actuator。
- `Docker Compose`：服务定义、端口映射、环境变量、volume、healthcheck。
- `YAML`：层级配置、环境隔离、敏感信息外置。
- 工程规范：包结构、模块边界、`.gitignore`、`.gitattributes`。

### 实践验证

- 能执行 `mvn test`。
- 能启动 `docker compose up -d mysql redis kafka`。
- 能执行 `mvn spring-boot:run`。
- 能访问 `/actuator/health`。

### 面试表达

> 项目采用模块化单体起步，先保持部署简单和领域边界清晰，后续可按资产、订单、撮合、清算、事件、对账拆分服务。

## 3. 用户资产与资金流水

### 功能点

- 创建用户资产账户。
- 模拟充值。
- 查询资产余额。
- 可用余额与冻结余额分离。
- 下单冻结。
- 撤单解冻。
- 成交扣减冻结资产。
- 成交入账。
- 记录不可变资金流水。

### 需要学习的知识模块

- `MySQL` 事务：`@Transactional`、提交、回滚、传播行为。
- `MySQL` 锁：行锁、间隙锁、死锁、`select ... for update`。
- `MySQL` 约束：唯一索引、非负约束、业务唯一号。
- 账务模型：可用余额、冻结余额、总余额、资产流水、业务单号。
- 幂等设计：充值幂等、冻结幂等、清算幂等。
- 金额处理：`BigDecimal`、精度、舍入、币种最小单位。
- 并发控制：乐观锁 `version` 与悲观锁的取舍。
- 审计思维：流水只追加，不修改，不删除。

### 实践验证

- 重复充值请求不会重复入账。
- 余额不足时冻结失败且余额不变。
- 并发冻结不会导致可用余额为负。
- 每次余额变化都能找到对应资金流水。

### 面试表达

> 资产模块以 MySQL 为资金正确性的最终依据，通过可用余额和冻结余额拆分、业务唯一号幂等、不可变资金流水和事务边界保证资产变更可追溯、可恢复。

## 4. 交易对与基础风控

### 功能点

- 配置交易对，例如 `BTC/USDT`。
- 维护基础资产、计价资产。
- 维护价格精度、数量精度、最小下单数量。
- 校验交易对是否启用。
- 校验下单价格和数量是否合法。
- 限制用户下单频率。

### 需要学习的知识模块

- CEX 基础概念：交易对、base asset、quote asset、tick size、lot size。
- 参数校验：Bean Validation、统一错误码、请求 DTO。
- 精度校验：价格精度、数量精度、最小交易单位。
- Redis 限流：固定窗口、滑动窗口、令牌桶。
- 风控边界：确定性规则先行，AI 只能解释规则。
- 缓存策略：交易对配置缓存、缓存失效、配置变更一致性。

### 实践验证

- 禁用交易对不能下单。
- 价格和数量精度不合法时不能冻结资产。
- 用户超出下单频率时被限流。
- 风控拒绝不产生订单和资金流水。

### 面试表达

> 下单前先经过交易对、精度、最小数量、账户状态和频率限制校验，只有确定性规则通过后才进入冻结和订单创建，避免无效订单污染撮合链路。

## 5. 订单生命周期

### 功能点

- 限价买单。
- 限价卖单。
- 订单创建。
- 订单状态机。
- 部分成交。
- 全部成交。
- 撤单。
- 查询订单。

### 需要学习的知识模块

- 状态机设计：状态枚举、合法流转、非法状态保护。
- 订单领域模型：委托数量、已成交数量、剩余数量、冻结金额。
- MySQL 更新条件：基于当前状态的条件更新，避免并发覆盖。
- 事务边界：订单创建和资产冻结同事务。
- 幂等请求：客户端请求号、订单号、唯一约束。
- 并发场景：撤单与成交同时发生时的处理。
- API 设计：下单接口、撤单接口、订单查询接口。

### 实践验证

- 下单成功后订单为 `NEW` 且资产已冻结。
- 部分成交后订单为 `PARTIALLY_FILLED`。
- 全部成交后订单为 `FILLED`。
- 已成交订单不能撤单。
- 重复撤单不会重复解冻资产。

### 面试表达

> 订单状态流转采用显式状态机和条件更新保护，撤单、成交、清算都必须基于当前状态进行校验，避免重复成交、重复解冻和非法状态跳转。

## 6. 内存订单簿与撮合

### 功能点

- 买盘订单簿。
- 卖盘订单簿。
- 价格优先。
- 时间优先。
- 限价单撮合。
- 部分成交。
- 生成成交记录。
- 服务重启后订单簿恢复方案。

### 需要学习的知识模块

- CEX 撮合规则：bid、ask、spread、maker、taker。
- 数据结构：`TreeMap`、优先队列、FIFO 队列。
- 排序规则：买盘价格倒序、卖盘价格正序。
- 算法复杂度：插入、查找最优价、撮合循环。
- 并发控制：单交易对串行撮合、队列化、锁粒度。
- 内存状态与持久化：订单簿快照、开放订单恢复。
- 边界条件：部分成交、剩余数量、价格相等、订单取消。

### 实践验证

- 买价大于等于卖价时成交。
- 买盘高价优先，卖盘低价优先。
- 同价订单按时间先后成交。
- 大单可以吃掉多个小单。
- 未成交剩余数量继续挂在订单簿。

### 面试表达

> 第一版撮合采用单交易对内存订单簿，买盘用价格倒序、卖盘用价格正序，同价位使用 FIFO 队列，保证价格优先、时间优先。数据库负责持久化订单状态，服务重启可根据开放订单恢复订单簿。

## 7. 成交清算

### 功能点

- 根据成交记录更新买方资产。
- 根据成交记录更新卖方资产。
- 扣减冻结资产。
- 增加成交所得资产。
- 释放买单多冻结金额。
- 记录清算结果。
- 清算失败重试。

### 需要学习的知识模块

- 清算模型：成交、买方入账、卖方入账、手续费预留。
- MySQL 事务边界：一笔成交的买卖双方资产更新。
- 幂等清算：`deal_no`、`settlement_no`、唯一约束。
- 分布式一致性：先同步清算，再扩展异步清算。
- 异常补偿：清算失败状态、重试任务、人工审核。
- 金额精度：成交金额、手续费、余款释放。
- 账务一致性：成交记录、资产流水、余额三者可对齐。

### 实践验证

- 同一成交重复清算只生效一次。
- 买方得到基础资产，卖方得到计价资产。
- 买方冻结金额按成交金额扣减，多余部分释放。
- 清算失败可以被任务发现并重试。

### 面试表达

> 清算模块以成交记录为输入，通过清算唯一号保证幂等，买卖双方资产变更和资金流水在事务内完成。失败清算会进入可重试状态，并由对账补偿任务兜底。

## 8. Kafka 事件与 Outbox

### 功能点

- 订单创建事件。
- 订单撤销事件。
- 撮合成交事件。
- 清算完成事件。
- 资产变更事件。
- outbox 事件表。
- Kafka 发布。
- 消费幂等。
- 失败重试。
- 死信事件。

### 需要学习的知识模块

- Kafka 基础：topic、partition、consumer group、offset。
- Producer：acks、retries、幂等生产者、发送回调。
- Consumer：手动提交 offset、重复消费、消费失败。
- 顺序性：同一订单或交易对消息 key 设计。
- 最终一致性：本地事务 + outbox + 异步发布。
- 幂等消费：消费记录表、唯一约束、状态机。
- 消息积压：消费速率、批量消费、扩容消费者。
- 死信队列：不可恢复失败与人工处理。

### 实践验证

- 数据库事务提交后一定有 outbox 事件。
- Kafka 暂时不可用时事件保持待发送。
- 重复消费不会重复清算或重复通知。
- 消费失败能重试，超过阈值进入死信。

### 面试表达

> 核心交易数据先落 MySQL，同时写 outbox 事件，后台发布到 Kafka。消费端通过事件 ID 和消费者组唯一约束保证幂等，解决数据库提交成功但消息发送失败的问题。

## 9. Redis 缓存与限流

### 功能点

- 交易对配置缓存。
- 盘口缓存。
- 最新成交价缓存。
- 用户下单限流。
- 热点数据读取优化。

### 需要学习的知识模块

- Redis 数据结构：String、Hash、ZSet、Stream 的适用场景。
- 缓存模式：Cache Aside、TTL、主动失效。
- 缓存一致性：更新数据库后删除缓存、延迟双删、最终一致。
- 热点 key：识别、拆分、本地缓存。
- 大 key：风险、拆分、扫描。
- 限流算法：固定窗口、滑动窗口、令牌桶。
- 分布式锁：什么时候需要，锁超时、续期、误删风险。

### 实践验证

- 盘口查询不直接打到数据库热点路径。
- 交易对配置变更后缓存可失效。
- 高频下单会被限流。
- Redis 故障不影响资金正确性。

### 面试表达

> Redis 在项目中用于读优化、热点数据和限流，不作为资金正确性的最终依据。资金和订单状态以 MySQL 为准，缓存允许短暂不一致但必须可恢复。

## 10. 对账与补偿

### 功能点

- 订单成交数量对账。
- 成交清算状态对账。
- 资产余额和资金流水对账。
- 冻结余额和未完成订单对账。
- outbox 事件发送状态对账。
- Kafka 消费状态对账。
- 创建补偿任务。
- 重试补偿任务。

### 需要学习的知识模块

- 对账思维：业务事实、派生数据、校验口径。
- SQL 汇总：`group by`、聚合、分页扫描、批处理。
- 定时任务：Spring Scheduler、任务幂等、任务分片预留。
- 补偿设计：可自动补偿与需人工审核的边界。
- 异常分类：数据缺失、状态错误、重复事件、处理超时。
- 可恢复性：重试次数、下次重试时间、失败原因记录。
- 审计报告：对账批次、差异明细、处理结果。

### 实践验证

- 篡改订单已成交数量后，对账能发现差异。
- 未清算成交能生成补偿任务。
- 未发送 outbox 事件能被重新发送。
- 资金流水无法解释的余额差异进入人工审核。

### 面试表达

> 对账不是简单定时任务，而是用订单、成交、清算、资产流水和事件状态互相校验。可自动恢复的差异进入补偿任务，不可自动恢复的资金异常进入人工审核。

## 11. 行情查询

### 功能点

- 查询盘口。
- 查询最近成交。
- 查询最新价。
- 后续扩展 K 线。
- 后续扩展 WebSocket 推送。

### 需要学习的知识模块

- 行情基础：盘口、深度、最新价、成交明细、K 线。
- 读模型设计：从撮合结果生成查询视图。
- Redis 缓存：盘口快照、最新成交、TTL。
- 查询性能：分页、索引、冷热数据。
- WebSocket 基础：连接管理、订阅、广播、心跳。
- 数据最终一致：行情可以异步更新，但核心成交记录必须准确。

### 实践验证

- 撮合后最近成交可查询。
- 最新价随最新成交更新。
- 买卖盘口按市场优先级排序。
- Redis 缓存失效后可从内存或数据库恢复。

### 面试表达

> 行情模块是核心交易的读侧视图，允许异步和缓存优化，但不能反向影响订单、撮合和清算结果。

## 12. 可观测性与压测

### 功能点

- 接口耗时指标。
- 订单创建 QPS。
- 撮合耗时。
- Kafka 积压监控。
- 失败事件数量。
- 慢 SQL 记录。
- 压测报告。

### 需要学习的知识模块

- Actuator：health、metrics、info。
- Micrometer：计数器、计时器、标签。
- Prometheus：指标抓取、查询。
- Grafana：面板、告警。
- 日志规范：traceId、orderNo、eventId、dealNo。
- 压测工具：JMeter 或 k6。
- 性能分析：慢 SQL、线程池、GC、CPU、内存。
- 容量评估：QPS、RT、错误率、瓶颈定位。

### 实践验证

- 能输出接口 QPS 和平均耗时。
- 能观察 Kafka 消费失败或积压。
- 能生成一份下单接口压测报告。
- 能说明瓶颈在数据库、锁、Redis、Kafka 还是代码。

### 面试表达

> 项目不仅实现功能，也关注线上可运维性，通过指标、日志、压测和对账报告定位性能瓶颈与一致性风险。

## 13. AI 辅助模块

### 功能点

- 风控规则解释助手。
- 交易异常解释助手。
- 日志故障归因助手。
- 项目知识库问答。
- AI 调用审计。
- AI 调用限流。

### 需要学习的知识模块

- LLM API：请求、响应、超时、重试、费用控制。
- RAG：文档切分、embedding、向量检索、重排序。
- Java AI 框架：Spring AI 或 LangChain4j。
- Tool Calling：让 AI 查询只读业务数据。
- 安全边界：敏感信息脱敏、权限校验、审计日志。
- 幻觉控制：引用来源、回答置信度、规则优先。
- 成本控制：缓存、限流、token 统计。

### 实践验证

- AI 可以解释某条风控拒绝原因。
- AI 可以基于项目文档回答设计问题。
- AI 不能修改订单、资产、清算状态。
- 每次 AI 调用都有审计记录。

### 面试表达

> AI 模块只做解释、归因和知识库问答，不进入确定性交易链路。核心交易保持规则驱动和可审计，AI 作为研发效率和运营辅助能力。
